# PolyQuant Pro — Polymarket BTC/ETH 量化套利研究与实时模拟交易系统

## 01. 项目角色

你是一名资深量化研究员、金融数据分析师、全栈架构师、Python 工程师、TypeScript 工程师、DevOps 工程师、安全工程师及软件测试工程师。

你的任务是从零设计并实现一个完整、专业、可持续运行、可持续改进的 Polymarket BTC/ETH 量化套利研究与实时模拟交易系统。

项目名称：PolyQuant Pro。

项目定位：

- 加密货币涨跌预测市场量化研究平台。
- 实时行情与盘口数据采集平台。
- 理论套利机会研究平台。
- 历史回测平台。
- 多策略实时模拟交易平台。
- 策略版本管理与对比实验平台。
- 策略盈利能力验证平台。
- 自动化收益分析与改进辅助平台。

项目不是简单的涨跌预测脚本，而是一套能够长期运行、积累数据、验证研究假设、发现问题和持续改进的完整系统。

## 02. 核心目标与基本原则

核心目标是在严格考虑市场规则、手续费、滑点、流动性、数据延迟、成交失败及极端行情的前提下，研究是否存在稳定、可重复、扣除成本后仍具有正期望收益的机会。

盈利能力是项目的核心研究目标，但不得承诺未经验证的收益，不得将高胜率等同于盈利，不得将概率性交易描述为确定性套利。

项目必须遵循以下原则：

1. 数据真实性优先于功能数量。
2. 净收益优先于胜率。
3. 风险控制优先于交易频率。
4. 样本外验证优先于历史拟合表现。
5. 可解释性优先于复杂模型。
6. 没有可靠研究优势时允许不交易。
7. 允许策略长期没有信号。
8. 允许最终研究结论为不存在可验证的盈利优势。
9. 禁止为了达到盈利目标而伪造数据或调整统计口径。
10. 第一版仅支持历史回测、影子运行和实时模拟交易。
11. 不连接真实资金账户，不自动执行真实下注，不需要钱包私钥。
12. 实盘交易不属于本项目当前开发范围。

## 08. 系统运行模式

系统必须支持以下四种运行模式。

### COLLECT_ONLY：纯数据采集

- 持续发现市场。
- 采集真实行情。
- 采集盘口。
- 采集结算数据。
- 保存历史记录。
- 不产生模拟订单。

### BACKTEST：历史回测

- 使用历史事件数据。
- 按历史时间顺序回放。
- 使用独立虚拟账户。
- 生成可重复的研究报告。
- 不影响实时模拟账户。

### SHADOW：影子研究

- 使用真实实时行情。
- 运行研究策略。
- 记录研究信号和理论机会。
- 记录机会最终结果。
- 不修改虚拟资金余额。
- 用于发现模型问题及评估数据质量。

### PAPER：实时模拟交易

- 使用真实实时行情。
- 使用虚拟资金。
- 使用保守模拟撮合。
- 维护虚拟持仓。
- 根据实际市场结算结果更新模拟账务。
- 实时统计收益及风险。
- 支持长期无人值守运行。

系统默认启动 COLLECT_ONLY 模式。

管理员可以在后台创建和启动 PAPER 模拟盘。

所有运行模式的数据必须隔离。

不得包含 LIVE 实盘交易模式、真实交易接口或钱包签名功能。

## 11. 策略研究框架

采用统一策略接口及插件式架构。

每个策略具有：

- strategy_id
- strategy_name
- strategy_version
- config_schema
- config_hash
- supported_market_types
- research_status
- implementation_hash
- created_at
- updated_at

策略接收标准化的市场状态及历史观测数据。

输出研究信号、模型解释、理论成本和研究结论。

所有研究信号必须可以追溯到具体的数据快照及策略版本。

### S00：基准对照策略

建立不交易基准、市场概率基准及其他可解释的研究基准。

用于判断复杂策略是否真正具有额外研究价值。

不得仅通过对比随机表现来宣称策略盈利。

### S01：互补合约套利研究

研究同一市场 UP 和 DOWN 合约总成本与固定兑付金额之间的关系。

研究模型必须考虑：

- 互补合约关系是否成立。
- 正常结算的前提。
- 两边报价是否同时有效。
- 实际订单簿深度。
- 两边成交不一致。
- 部分成交。
- 费用变化。
- 结算异常。
- 数据延迟。

区分以下研究结果：

- 表面价格偏差。
- 扣除费用后的理论价格偏差。
- 保守模拟条件下的可实现结果。
- 最终结算后的模拟收益。

不得将盘口展示价格直接认定为可成交价格。

不得假设双边必然同时成交。

### S02：尾盘结算统计研究

这是项目重点研究方向之一。

根据各市场实际官方结算规则，研究市场结束前的价格信息及最终结算结果之间的统计关系。

研究内容包括：

- 市场剩余时间。
- 开盘基准价格。
- 已观测结算相关价格。
- 未知价格区间。
- TWAP 计算规则。
- 短周期波动率。
- 价格反转情况。
- 极端行情。
- 数据源误差。
- 市场价格与最终结果的关系。

将尾盘时间窗口设计为可配置的研究变量。

通过独立实验比较不同时间窗口。

不得提前假设某个时间窗口必然盈利。

不得使用未来数据参与当前决策。

不得将模型高置信度解释为必然结果。

### S03：概率定价偏差研究

建立市场概率与实际结果之间的统计研究模型。

研究模型概率是否经过校准，以及考虑完整成本后是否存在正期望证据。

必须支持：

- Brier Score。
- Log Loss。
- 概率可靠性曲线。
- Expected Calibration Error。
- 样本外验证。
- 稳定性评估。
- 极端行情评估。

优先采用可解释的统计模型。

只有复杂模型在严格样本外实验中具有明确优势时，才允许纳入后续研究。

### S04：跨周期关系研究

研究：

- 同一资产不同时间周期之间的关系。
- 不同基准价格造成的结果差异。
- 不同结算窗口之间的影响。
- BTC 与 ETH 之间的统计相关性。

区分数学互补关系、条件性逻辑关系和统计相关性。

不得将普通相关性称为无风险套利。

第一阶段仅提供研究及模拟结果。

暂停、停止和恢复必须明确处理已有虚拟持仓和待处理模拟订单。

重置虚拟资金不能删除原始实验历史。

需要重置时，应归档原模拟账户并创建新的实验账户。

### 模拟盘状态机

- CREATED
- STARTING
- RUNNING
- PAUSED
- RISK_HALTED
- STOPPING
- STOPPED
- ERROR
- ARCHIVED

状态切换必须具备审计日志和幂等保护。

禁止出现重复运行实例。

禁止在服务重启后产生重复模拟成交。

## 13. 保守模拟撮合引擎

不得将策略信号出现时的盘口价格直接视为最终模拟成交价格。

模拟流程应考虑：

- 信号时间。
- 数据接收时间。
- 模拟订单创建时间。
- 模拟订单到达时间。
- 当时可观察的订单簿。
- 订单簿价格。
- 可用数量。
- 价格精度。
- 数量精度。
- 数据延迟。
- 手续费。
- 滑点。
- 部分成交。
- 完全未成交。
- 模拟订单取消。
- 市场停止接受订单。
- 市场结束。

模拟订单必须具有完整状态机。

至少包括：

- PENDING
- OPEN
- PARTIALLY_FILLED
- FILLED
- CANCELLED
- EXPIRED
- REJECTED

模拟撮合必须遵循因果时间顺序。

只能使用模拟订单到达时已知的市场数据。

不得假设 Maker 订单在价格触及时必然成交。

如果缺少队列信息，必须采用保守估计并标记不确定性。

对于无法合理模拟成交的情况，应标记为 UNVERIFIABLE，而不是强行填充成交结果。

支持基础、保守、压力测试等不同模拟假设版本。

每个实验必须固定撮合模型版本。

模拟成交记录应保存当时的完整假设及对应市场快照。

## 16. 多策略及多参数实验系统

## 17. 历史回测系统

- 历史成交事件。
- 历史价格数据。

- 模拟账务。
- 模拟风险控制。

回测引擎与实时模拟引擎应尽可能共享以下模块：

- 策略研究接口。
- 成本模型。
- 模拟撮合模型。
- 模拟资金账务。
- 结算模型。
- 风险控制。
- 结果评估。

避免出现回测实现与实时模拟实现完全不同的情况。

回测数据必须按照时间顺序划分训练集、验证集和测试集。

支持：

- Walk-forward Analysis。
- 样本外测试。
- Purged / Embargo 时间序列验证。
- Block Bootstrap。
- 参数敏感性研究。
- 成本压力测试。
- 延迟压力测试。
- 极端行情压力测试。

- 未来数据泄露。
- 幸存者偏差。
- 事后价格偏差。
- 成交假设过于乐观。
- 忽略亏损样本。
- 忽略未成交样本。
- 多重检验偏差。
- 规则版本混用。
- 反复使用测试集调参。

所有回测任务必须保存完整配置、随机种子、代码版本、数据集版本及结果摘要。

同一版本代码和数据应能够复现回测结果。

- 订单簿异常。

- 账务异常。

## 22. 策略持续改进系统

实现研究、评估、改进、验证的闭环。

基本流程：

实时模拟运行 → 积累真实数据 → 生成研究报告 → 分析亏损原因 → 提出改进假设 → 创建新策略版本 → 历史验证 → 新旧版本并行模拟 → 人工评审。

每个改进建议必须包含：

- 建议编号。
- 关联策略。
- 当前版本。
- 问题描述。
- 支持证据。
- 受影响样本。
- 研究假设。
- 建议实验。
- 潜在风险。
- 验证方案。
- 验收标准。
- 审核状态。

允许使用统计分析和可选 AI 辅助生成研究建议。

AI 只能用于：

- 阅读研究报告。
- 汇总异常。
- 分析研究结果。
- 提出待验证的假设。
- 生成实验计划。
- 辅助开发人员理解代码。
- 辅助生成研究文档。

AI 不得：

- 自主修改正在运行的策略。
- 自主提高风险限额。
- 自主覆盖历史实验。
- 自主认定某个策略已经稳定盈利。
- 根据短期亏损不断改变参数。
- 伪造或修改研究结果。

### Champion / Challenger 机制

将当前已经建立研究基线的策略版本标记为 Champion。

新研究版本标记为 Challenger。

两者必须使用独立模拟账户并行运行。

比较时尽量使用相同时间范围、市场范围、初始虚拟资金、成本模型和撮合假设。

新版本只有通过预先定义的验证条件及人工审核后，才允许成为新的研究基线。

保留旧版本配置、历史表现及对应数据。

支持版本回滚，但不得删除新版本的历史记录。

## 23. 盈利能力验证

盈利能力是研究目标，不是预先承诺的结果。

初始研究验收门槛建议如下：

- 至少 90 天历史研究数据。
- 按市场结算规则版本分别分析。
- 至少 1000 笔样本外有效模拟成交。
- 至少连续 30 天实时模拟运行。
- 扣除完整成本后净收益大于零。
- Profit Factor 大于 1.3。
- 最大回撤不超过 5%。
- 成本增加 50% 后仍有正收益证据。
- 延迟压力测试符合预先设定条件。
- 净期望收益的 95% 置信区间下界大于零。
- 不依赖单一极端盈利事件。
- 不依赖未经验证的模拟成交假设。
- 数据质量符合预先设定要求。
- 通过多重检验偏差控制。

以上数值属于初始研究门槛，需要结合有效样本数量及统计功效分析进行评估。

不得在看到研究结果后随意降低门槛。

必须区分：

- NOT_STARTED：未开始。
- COLLECTING_DATA：数据采集中。
- INSUFFICIENT_DATA：数据不足。
- UNDER_RESEARCH：研究中。
- BACKTEST_FAILED：回测未通过。
- PAPER_TESTING：模拟验证中。
- VALIDATION_FAILED：验证未通过。
- VALIDATION_PASSED：达到预设研究验收标准。
- SUSPENDED：研究暂停。

VALIDATION_PASSED 仅代表达到指定研究条件，不代表未来收益保证，也不自动启用实盘功能。

遇到无法访问真实数据、无法确认市场规则、关键测试失败或其他阻塞问题时，必须记录真实原因。

优先交付能够持续采集数据和运行实时模拟盘的 MVP。

之后持续完善回测、实验分析、策略评估和改进模块。

每次开发会话结束前，必须更新 AGENTS.md、TASKS.md、CHANGELOG.md 和必要的架构文档，使后续 AI 会话能够无缝继续。

项目最终成功标准不是实现一个能够频繁下注的程序，而是实现一套真实、稳定、可重复、可审计、能够长期运行并科学判断策略盈利能力的量化研究与实时模拟交易系统。

始终遵循：先验证，再下结论；数据不足，不宣称盈利；模拟资金与真实资金严格隔离。

在既有研究流程之外，为 Polymarket 国际站增加可选账户配置。管理员选择已运行的 PAPER 账户及策略版本，保存公开钱包地址、单笔买入本金上限和同钱包累计买入本金上限，检查账户与地区状态，显式启用后才可自动提交新信号。授权关闭为默认状态。实际手续费独立按币种展示，未确认的费用显示待核对。模拟资金与回测结果仍独立核算。
